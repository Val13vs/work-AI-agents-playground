Test 4 — Multi-step flow + Sub-Agent
============================================================

Препоръчително:
    Стартирайте New chat.

В интерфейса изпратете:
    Analyze DEV-101 and give me a detailed Angular frontend implementation plan.

Очакваме:
    Agent-ът първо да намери DEV-101.

    След това да установи:
        relatedApi = Locations

    След това да намери Locations API документацията.

    Накрая да използва Frontend Specialist Agent
    за изготвяне на Angular implementation plan.

В backend terminal-а трябва да се вижда поне:
    [TOOL] get_ticket called with ticketId=DEV-101
    [TOOL] get_api_documentation called with resource=Locations

Очакваният логически flow е:
    Coordinator Agent
    ↓
    get_ticket
    ↓
    DEV-101
    ↓
    relatedApi = Locations
    ↓
    get_api_documentation
    ↓
    Locations API documentation
    ↓
    Frontend Specialist Agent
    ↓
    Coordinator Agent
    ↓
    Final response

Крайният отговор трябва да съдържа практичен Angular план,
например когато е приложимо:
    components
    services
    models/interfaces
    API calls
    state handling
    loading/error handling
    pagination
    filters

Това доказва:
    един user request
    ↓
    може да изисква няколко последователни действия
    ↓
    Coordinator Agent използва няколко tools
    ↓
    делегира специализиран reasoning на Sub-Agent
    ↓
    връща един финален резултат

Test 6 — Guardrail блокира невалиден status transition
============================================================

Преди теста проверете:
    GET http://localhost:3000/api/tickets/DEV-102

Очакван начален статус:
    OPEN

Препоръчително:
    Стартирайте New chat.

В интерфейса изпратете:
    Change DEV-102 status to DONE.

Според business rules:
    OPEN → DONE
    е НЕвалиден transition.

Очакваме:
    Guardrail-ът да блокира операцията.

    Approval card НЕ трябва да се показва.

    Ticket-ът НЕ трябва да бъде променен.

В backend terminal-а не трябва да се вижда:
    [TOOL] update_ticket_status executing: DEV-102 -> DONE

След заявката проверете отново:
    GET http://localhost:3000/api/tickets/DEV-102

Очакваният статус остава:
    OPEN

Очакваният flow е:
    User request
    ↓
    Coordinator Agent
    ↓
    update_ticket_status request
    ↓
    Input Guardrail
    ↓
    OPEN → DONE
    ↓
    BLOCKED
    ↓
    няма approval
    ↓
    няма execute()
    ↓
    няма промяна на данните

Това доказва:
    LLM не е финалната authority за business rules
    ↓
    Guardrail-ът програмно валидира операцията
    ↓
    невалидни действия не стигат до execution

Test 7 — Human Approval / Reject
============================================================

Преди теста DEV-102 трябва да бъде:
    OPEN

Ако е необходимо:
    рестартирайте Backend-а, за да се върнат mock данните.

Препоръчително:
    Стартирайте New chat.

В интерфейса изпратете:
    Change DEV-102 status to IN_PROGRESS.

Този transition е валиден:
    OPEN → IN_PROGRESS

Очакваме:
    Guardrail-ът да разреши операцията.

    Tool-ът да НЕ се изпълни веднага.

    В интерфейса трябва да се покаже Human Approval card.

Approval card трябва да показва приблизително:
    Human approval required

    Tool:
        update_ticket_status

    Arguments:
        ticketId = DEV-102
        status = IN_PROGRESS

    Actions:
        Reject
        Approve action

ПРЕДИ да натиснете Reject проверете:
    GET http://localhost:3000/api/tickets/DEV-102

Очакваният статус все още е:
    OPEN

След това натиснете:
    Reject

Очакваме:
    Agent workflow-ът да продължи след rejection-а.

    Tool-ът НЕ трябва да се изпълни.

В backend terminal-а не трябва да се вижда:
    [TOOL] update_ticket_status executing: DEV-102 -> IN_PROGRESS

Проверете отново:
    GET http://localhost:3000/api/tickets/DEV-102

Очакваният статус остава:
    OPEN

Очакваният flow е:
    User request
    ↓
    valid Guardrail
    ↓
    approval_required
    ↓
    Human selects Reject
    ↓
    RunState.reject(...)
    ↓
    Agent run resumes
    ↓
    tool НЕ се изпълнява
    ↓
    данните не се променят

Това доказва:
    валидно действие
    ≠
    автоматично разрешено действие

    Human-in-the-loop
    ↓
    човекът запазва крайния контрол

    [TOOL] update_ticket_status executing: DEV-102 -> IN_PROGRESS

    GET http://localhost:3000/api/tickets/DEV-102

Очакваният нов статус е:
    IN_PROGRESS

че операцията е извършена успешно.

Очакваният flow е:
    User request
    ↓
    update_ticket_status
    ↓
    Guardrail
    ↓
    VALID
    ↓
    Human Approval
    ↓
    Approve
    ↓
    RunState.approve(...)
    ↓
    resume Agent run
    ↓
    execute()
    ↓
    DEV-102 = IN_PROGRESS

Това доказва:
    Agent може да предлага write action
    ↓
    Guardrail проверява дали е допустимо
    ↓
    човекът го разрешава
    ↓
    paused workflow продължава
    ↓
    tool извършва реална промяна
